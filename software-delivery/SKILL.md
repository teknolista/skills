# Deliver a software change

Turn an authorized outcome into working, verified software. Use the domain workflow directly for a localized change and its regression checks. Write artifacts in English and converse in the user's language.

1. **Establish the contract.** Read the request, project guidance, and the affected implementation and callers. Locate the governing baseline and any accepted active change, retaining their acceptance criteria and IDs. Keep proposals separate. Without a formal specification, use the request, existing contracts, callers, tests, and decisions. Identify the target checkout and platforms. For a material behavior or boundary change, consequential uncertainty, or an explicit specification requirement, use [change contracts](references/change-contracts.md) before editing the affected behavior. Read its worked examples when implementing an accepted OpenSpec change or promoting an experiment into maintained software. Use the porting or generated-source guidance when it applies. Resolve routine choices within delegation. A planning-only request ends with the plan.
2. **Choose verifiable increments.** Reuse the authoritative plan or tracker. If none exists, keep a short plan in the conversation, or save one when durable coordination is needed and writing is authorized. Each task names its outcome, owning paths, consumed/produced contracts, prerequisites, acceptance check, and evidence needed for completion. Start with a useful path through the real entry point. Shared schema and interface changes must agree before dependents begin. For refactors or substantial module design, read [code design](references/code-design.md).
3. **Establish the baseline.** Inspect required commands and their side effects, including hooks and service targets. Run relevant safe baseline checks when they will distinguish inherited failures. Reuse project tooling and lockfiles. Before installing a new dependency, verify its exact package, publisher and version against an approved source. Set up missing prerequisites within task authority. For isolation, parallel work, automation, or manual prerequisites, read [execution controls](references/execution-controls.md).
4. **Implement one coherent task.** Read its contracts and affected consumers, make the smallest complete change, and verify its observable behavior. Use the relevant project or specialist procedure. Preserve existing work and meaningful tests. A requested or required test-first workflow observes the intended failing assertion before the fix. Diagnose unclear failures before attempting fixes. Reassess scope when new evidence exposes a consequential assumption or wider effect. Pause dependent work while reconciling the governing contract and continue authorized independent work.
5. **Integrate and review.** Check the combined result against the accepted outcome and applicable standards. Run required safe checks on the resulting snapshot, including affected integrations and compatibility. Classify inherited, introduced, and unclassified failures. Evaluate review feedback against actual code and contracts, fix authorized defects, and recheck affected paths. Use a fresh reviewer when requested or required and available. Disclose self-review and unmet independence requirements instead of inventing approval.
6. **Record and finish.** Record completed and pending work, changed paths or revision, decisions, actual checks, unresolved gates, and the next action. Compare the agreed change with the resulting behavior, contracts and checks. Update affected records in their authoritative homes within scope, or report pending updates in the handoff. When PentaPRO exists, keep PROCESS as the shared index and PROOF as the evidence owner. Reopen relevant source on resumption. Completion requires the requested behavior, reconciled material contracts, and required verification. Unavailable mandatory evidence leaves the affected gate incomplete.

Do not equate task completion with commit, push, tracker closure, merge, deployment, or acceptance. Continue those actions only under their actual authorization. Report outcome, changes, verification and material limits. A trial that succeeded on one platform does not prove every target works.

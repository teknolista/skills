# Deliver a software change

Turn an authorized outcome into working, verified software in the existing project. Use the same method for web, mobile, desktop, services, libraries, and developer tools. Write artifacts in English and converse in the user's language. This skill coordinates implementation, not every conversation.

1. **Establish the contract.** Read the request, project guidance, relevant source and callers, accepted requirements, and existing task record. Identify the target checkout, current changes, supported platforms and tool versions. Separate requested behavior from proposals. Resolve routine implementation choices within delegation. Ask only about consequential gaps that change the outcome or authority, and continue independent work. A planning-only request ends with the plan.
2. **Choose verifiable increments.** Reuse the authoritative plan or tracker. If none exists, keep a short plan in the conversation, or save one when durable coordination is needed and writing is authorized. Each task names its outcome, owning paths, consumed/produced contracts, prerequisites, acceptance check, and evidence needed for completion. Start with a useful path through the real entry point. Shared schema and interface changes must agree before dependents begin. For refactors or substantial module design, read [code design](references/code-design.md).
3. **Establish the baseline.** Inspect required commands and their side effects, including hooks and service targets. Run relevant safe baseline checks when they will distinguish inherited failures. Reuse project tooling and lockfiles. Set up missing prerequisites only within task authority. For isolation, parallel work, automation, or manual prerequisites, read [execution controls](references/execution-controls.md). No external skill or orchestration tool is required.
4. **Implement one coherent task.** Read its contracts and affected consumers, make the smallest complete change, and verify its observable behavior. Use the project's specialist procedure for actual UI, API, MCP, native data, or test work when available. A requested or project-required test-first workflow observes the intended failing assertion before the fix. Otherwise use checks proportionate to the risk, preserving existing work and meaningful tests. An unclear failure calls for diagnosis rather than successive speculative patches.
5. **Integrate and review.** Check the combined result against the accepted outcome and applicable standards. Run required safe checks on the resulting snapshot, including affected integrations and compatibility. Classify inherited, introduced, and unclassified failures. Evaluate review feedback against actual code and contracts, fix authorized defects, and recheck affected paths. Use a fresh reviewer when requested or required and available. Disclose self-review and unmet independence requirements instead of inventing approval.
6. **Record and finish.** Record completed and pending work, changed paths or revision, decisions, actual checks, unresolved gates, and the next action. Update the existing task record when authorized, or include the handoff in the response. When PentaPRO exists, keep PROCESS as the shared index and PROOF as the evidence owner, linking existing task records. Reopen relevant source on resumption. Completion requires the requested behavior, reconciled contracts, and required verification. Unavailable mandatory evidence leaves the affected gate incomplete.

Do not equate task completion with commit, push, tracker closure, merge, deployment, or acceptance. Continue those actions only under their actual authorization. Report outcome, changes, verification and material limits. A trial that succeeded on one platform does not prove every target works.

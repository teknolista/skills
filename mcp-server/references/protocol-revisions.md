# MCP protocol revision checks

Use the revision supported by each actual client and SDK. Keep a compatibility record with client, SDK version, protocol revision, transport, capabilities used, and observed checks. A trace establishes what reached an endpoint and how it responded. Confirm the contract in the selected specification and confirm implementation support separately.

## 2026-07-28

- Each request declares protocol version and client capabilities in `_meta`. The server implements `server/discover`, and clients can discover first or send a supported request directly. Test an unsupported modern revision and the `UnsupportedProtocolVersionError` response. On Streamable HTTP, verify `MCP-Protocol-Version` and `Mcp-Method` and, for named operations, `Mcp-Name`. Confirm header/body mismatches are rejected before dispatch. Use the body and authenticated caller for authorization decisions.
- Preserve transport-specific cancellation and streaming behavior. Streamable HTTP can use request-scoped SSE responses. A lost response stream is retried as a new request with a new protocol request ID. For an operation promising deduplication, retain its application idempotency key across that retry and verify the durable effect count after a lost response, including any race with the first attempt. Use the supported subscription mechanism when the contract needs unsolicited change notifications.
- For cacheable discovery and resource results, set the required `ttlMs` and `cacheScope` according to freshness and access. Keep caller-specific results out of shared caches. Return tool listings in a stable order and check that a second principal cannot receive the first principal's private result.
- Keep application state behind explicit handles when calls need to continue earlier work. Resolve the handle under the authenticated principal, action, resource, and scope before use. Exercise a permitted handle and one replayed by a different caller. Check expiry or revocation when promised.
- For multi round-trip requests, use `input_required` and verify the retry of the original request with the client's responses and any echoed `requestState`. Apply integrity protection when the state influences authorization, access or business logic. Bind and check the relevant request, principal and validity window. For a single-use effect, enforce one-time consumption server-side. Check tampering, cross-principal or cross-request replay, and duplicate continuations against downstream effects.
- Use Apps, Tasks, and other extensions when the required capability is supported by both peers, and verify fallback or rejection otherwise. Keep deprecated HTTP+SSE, Roots, Sampling, Logging, and Dynamic Client Registration on compatibility paths where existing clients require them. Follow the selected transport and OAuth rules, including issuer and audience validation at their respective boundaries.

## 2025-11-25 and dual-era deployments

Preserve the supported `initialize` and `notifications/initialized` exchange for legacy clients. For authenticated stateful HTTP, validate credentials on every protected request, including supported stream resumption. Bind session state to the principal. Replay a valid session identifier without credentials and with a different principal, and verify rejection before data or effects. Follow the legacy revision's origin and binding rules.

When one endpoint serves both eras, exercise the real revision selection for both clients. Check that a valid modern first call reaches its handler without legacy initialization and that legacy clients retain their original lifecycle. Verify modern version errors and transport-specific fallback separately. Where both paths share a write service, verify that equivalent retries through supported paths cannot duplicate the promised application effect.

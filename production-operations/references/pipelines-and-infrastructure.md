# Pipelines and infrastructure

## Define resource ownership and the bootstrap

Inventory existing resources and their owners before generating a stack. If adopting manual resources, map exact IDs and review import and post-import plans before managing them. Preserve shared resources, avoid overlapping deploy controllers, and keep environment state separate with scoped access, encryption, versioning, and locking where supported. Treat state and saved plans as sensitive. Verify the remote backend, workspace or stack, account and region explicitly. Bootstrap state storage, federation, registry and vault access through the established trusted path. If bootstrap credentials are temporary, verify their expiry or revocation when in scope.

Use the repo's IaC and deployment conventions, whether native templates, Terraform/OpenTofu, Pulumi, GitOps or maintained host automation. Pin provider/tool versions consistently. Review replacement, deletion, IAM changes, public exposure, DNS, data, quotas and recurring cost in the target plan. Bind an apply to the reviewed plan or equivalent authoritative diff, exact inputs and target. Re-plan and review if state, inputs, policy, plan age or target make the result stale. Serialize changes to shared resources with the owning controller or environment lock. After a failed or timed-out apply, reconcile operation status, resource IDs and state before resuming. Never force-unlock an active writer or apply a different workspace as a recovery shortcut.

## Build, promote and verify

1. **Unprivileged verification.** Run relevant tests, lint, IaC validation and build checks with minimal permissions. Separate untrusted PR code and outputs from privileged runners, protected secrets, deployment credentials and writable shared caches. Check actual workflow triggers, reusable workflows, environment protection, runner identity and permission defaults. A workflow merged to the default branch may activate deployment.
2. **Trusted packaging.** Build once where the platform permits and record commit, artifact digest or provider version, platform/architecture, dependency locks and configuration source. Use the project's integrity checks and attestations when required. If a platform builds from source per environment, prove exactly which source and produced artifact were deployed in each. Keep build secrets out of image layers, build arguments, artifact contents and logs.
3. **Targeted release.** Promote a pinned artifact through the project-defined environments. Apply only the reviewed target configuration, use environment-scoped credentials, pass secret references to the runtime, and put schema jobs in the agreed order. Pin CI actions or plugins to reviewed immutable versions where supported. Use deployment-level concurrency and leave started irreversible jobs running to a known state unless their documented cancellation is safe.
4. **Independent evidence.** Poll bounded provider status, then verify through actual ingress or event sources using scoped synthetic data. Compare the expected artifact with the serving revision, distinguish smoke results from control-plane status, and store run/operation IDs and sanitized evidence. Gate further promotion on observed checks and a viable recovery path.

For Kubernetes, confirm cluster, context and namespace, render and inspect the Helm/Kustomize/manifests or GitOps diff, verify registry pull and workload identity, and check resource quotas, probes, rollout and disruption settings. Check revisions and image IDs in ready Pods and test through the intended ingress. StatefulSet changes require storage and ordered rollout checks. A workload rollback does not revert external secrets, CRDs, schemas or queued work. Reconcile rollbacks with GitOps desired state so the controller does not reapply the failed revision.

For network or DNS changes, inventory records, TTL, certificate names, validation, ingress ACLs, proxy/CDN behavior and origin health before the cutover. Prevalidate the new path with the intended Host/SNI and authentication when possible. Account for cached answers, IPv4/IPv6, connection draining and both origins serving simultaneously. Verify authoritative records, representative resolvers, TLS and application behavior from outside the control plane. Keep old capacity available for the defined transition.

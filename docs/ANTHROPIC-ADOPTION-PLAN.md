# Anthropic practices and the Teknolista skills improvement plan

Assessment dated 2026-11-11. Collection baseline `94057176ddaa6a355be1264549bae02c316bbd4d` on `main`, with 22 installable skills. This is a proposal based on the supplied `relatorio_anthropic_dev_workflow.md`, selected first-party sources, the current collection, and a temporary OpenSpec CLI probe.

## Implementation status

The first implementation shipped in Software Delivery 1.3.0, PentaPRO 2.8.0 and Agent Instructions 1.1.0. The collection runner offers Linux mount/process isolation, a synthetic OpenSpec change, and seeded and clean receipt controls. See the [pilot setup](../README.md#start-a-pilot), [evaluation procedure](../SKILL-EVALUATION.md), and [recorded checks](../evals/RESULTS.md#anthropic-adoption-pilot-preparation). The priorities below describe the initial proposal. Product adoption and matched real-model results remain pilot work.

## Workflow for adopting projects

| Work | Where intent lives | Minimum observable evidence |
| --- | --- | --- |
| Clear and reversible local change | Existing request, ticket, or contract. Use the domain workflow directly. | Focused check of the affected behavior or rendering and inspection of the scoped diff. |
| Vibe coding to explore feasibility or UX | Short question, limits and success signal in the request. Use an isolated project or branch with synthetic data and appropriately scoped tools. | Running prototype or experiment result, conditions exercised, and open questions. On promotion, review reused code and dependencies, resolve temporary shortcuts, establish maintained behavior and run the appropriate delivery checks. |
| Consequential change with an established lightweight process | Existing issue, schema, or equivalent governing record with behavior, material decisions, failure scenarios and checks. | Acceptance at the affected boundary, plus compatibility or negative checks when relevant. |
| SDD selected by user or project policy | Accepted change in the project's native workflow, including OpenSpec when selected. PentaPRO provides broader specification work where needed. | Validate the artifacts, exercise the requirement scenarios through the product, and attach revision-specific evidence. |
| Higher consequence in any route | Use the existing governing record and escalate specification depth when the contract is insufficient. Review authority, identity, and expected effects separately. | Examples include a tenant-denial check that reaches the authorization boundary, a migration rehearsal and recovery check, or a read-only independent review of the exact revision. Apply the project's actual gates and release authority. |

A one-line authorization change can warrant a strong contract and independent verification. A broad visual experiment can remain lightweight while isolated. A well-defined OpenSpec change with a localized implementation can go directly to its domain owner. ## OpenSpec pilot

1. Use the project's installed OpenSpec version and selected schema. In the default schema, the proposal records intent and impact, the specification delta records observable requirements, design records technical choices when needed, and tasks track implementation. Establish acceptance from project authority. Where PentaPRO is used, link canonical behavior from PRODUCT, link executed evidence from PROOF, link change design from PROJECT, retain operating constraints in PRODUCTION, and point PROCESS to the active task list. A project without PentaPRO can retain evidence in its existing PR or verification record. [OpenSpec default schema](https://openspec.dev/docs/schemas/spec-driven) · [PentaPRO ownership](../penta-pro/references/document-maintenance.md#existing-change-and-specification-workflows)
2. Pilot a tenant-scoped receipt change. Add scenarios for legitimate retrieval and a caller using another tenant's receipt ID. When a write changes, cover replay or partial failure where applicable. Verify through the real service entry point and inspect the relevant state. An independent reviewer receives the accepted scenario, diff, exact revision and check outputs and confirms the negative request reached the guard.
3. Use the optional OpenSpec verification skill where the installed profile provides it. Its comparison report complements execution evidence. Record the validated change, scenario-to-check links and results for the tested revision. If implementation exposes a conflict, resolve the owning decision and recheck the affected scenario. Archive according to the project's workflow after reconciling spec, tasks and evidence, then validate the resulting capability. [OpenSpec Verify](https://openspec.dev/docs/skills#openspec-verify-change) · [Collection worked example](../software-delivery/references/change-contracts.md#worked-example-with-openspec)

**CLI probe.** In a disposable directory with OpenSpec 1.16.0, a fixture had valid proposal, design, requirement scenario and an unchecked task. `openspec status --change tenant-receipts --json` returned `isComplete: true`. `openspec validate tenant-receipts --strict --json` passed, and `openspec instructions apply --change tenant-receipts --json` reported zero of one task complete. Removing the scenario made strict validation exit 1. This establishes artifact readiness and a structural negative control. The probe contained no product implementation. The `delivery-sdd` case exercises a lightweight SDD overlay. The separate `delivery-openspec` case includes a real OpenSpec baseline and delta, with two unchecked implementation tasks. ## Sequence and adoption criteria

| Priority and suggested window | Deliverable | Acceptance |
| --- | --- | --- |
| P0 · Weeks 1–2 | Pin the collection baseline and build isolated grading for a small set of existing cases plus one real OpenSpec fixture. Include localized copy, tenant isolation and scope-preserving review. | Evaluator and sibling trial files are inaccessible in a negative read probe. A deliberately broken implementation fails the external check, a known correct implementation passes, and a clean case receives no invented findings. Record raw outcomes per arm. |
| P1 · Weeks 3–4 | Add the smallest guidance changes supported by the baseline. Trial a direct task, a disposable prototype promoted to maintained code, and the real OpenSpec change. Add the worked example and revision-specific handoff to the relevant references. | The direct task remains scoped and light. The prototype crosses into maintained use only with reviewed dependencies and acceptance evidence. The OpenSpec case preserves canonical intent, handles a contract conflict, and distinguishes CLI validity from runtime behavior. A fresh session reopens the actual revision and continues from the pending check. |
| P2 · Weeks 5–8 | Pilot one real product repository and one disposable or staging environment under their actual policies. Compare advisory independent review with the existing workflow on a consequential change. Add a test for a concrete escaped defect. | Publish observed cost, latency, review effort, regressions and evidence gaps. Use hard gates only where the project owns the policy and both pass and fail behavior have been demonstrated. Prefer the simpler workflow when extra review adds no observed value. |

Run matched arms with the existing runner's baseline, candidate, and no-collection modes where useful. Pin fixture, host, model, reasoning, tools, limits and starting state. Separate natural discovery trials from explicit invocation. Start with three attempts per arm for the critical cases as an exploratory screen. Repeat finalists on a second relevant model or host before making portability claims. Capture acceptance on the first attempt and consistency across repeats, correct routing, unauthorized effects, confirmed defects missed, false positives, honest treatment of missing evidence, time and tokens. Review ambiguous outcomes and count timeouts and unavailable tools explicitly. Keep hidden grader material outside agent reach. [Collection evaluation procedure](../SKILL-EVALUATION.md) · [Anthropic evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

Reject candidates that allow a confirmed unauthorized effect, a bypass of a required check, or a false claim of required verification in the trial. Preserve behavior on clean and low-risk controls. Adopt a change when it demonstrates a repeatable improvement on its target failure with an acceptable time and cost tradeoff. Track rework and escaped defects in a defined pilot window. Report results by case, model, host and revision. The current trial record supports exploratory observations and leaves comparative reliability across real products and environments to the pilot.

## Maintain improvements from observed failures

For a recurring correction or escaped defect, preserve a sanitized reproducer and identify the layer that could have caught it. Put a repository-specific command or exception in the project's instructions, a reusable gotcha in the owning skill's conditional reference, and an enforceable property in a test or trusted CI check. Preserve one clean control to catch overcorrection. Retest the prompt that previously failed and record the candidate revision, observed result and decision in the existing evaluation record. Start with failures that expose data, weaken authorization, or produce unsupported verification claims, followed by avoidable routing and context cost.
